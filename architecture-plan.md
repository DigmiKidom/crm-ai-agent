# CRM AI Agent — Architecture Plan

## 1. What this is

A multi-tenant SaaS platform. A company signs up, answers a short set of questions about their business and preferences, and an AI agent picks a template/theme and generates a working landing page (for capturing leads) plus a configured CRM instance (contacts, pipeline stages, fields relevant to that business). It isn't fully custom design from scratch — the agent works within a set of pre-built templates and fills them in intelligently.

Stack chosen: Next.js (React + Node in one app), MongoDB for data, GitHub for source control, Vercel for hosting.

## 2. Tech stack

- **Framework**: Next.js (App Router). React for UI, Next's API routes / server actions serve as the Node backend — no separate server to deploy.
- **Database**: MongoDB Atlas, accessed via Mongoose (schema validation is worth the small overhead given how structured CRM data is).
- **Auth**: Auth.js (NextAuth) — credentials + optional Google OAuth, session tied to a tenant/company ID. Full detail in section 5.
- **Styling**: Plain CSS (CSS Modules per component, as requested) rather than a utility framework, so templates stay easy to theme via CSS variables.
- **AI agent**: Claude API (Anthropic), called server-side from a Next.js route, to (a) interview the company about preferences and (b) generate landing page copy/config and initial CRM setup from a chosen template.
- **Hosting/CI**: GitHub repo → Vercel, auto-deploy on push to main, preview deployments on PRs.

## 3. Multi-tenancy model

Each signed-up company is a **Tenant**. Two things need to be decided as the product matures, but the recommended starting point:

- **Data isolation**: single shared MongoDB database, every collection carries a `tenantId` field, all queries scoped by it. Simpler to operate than a database-per-tenant; fine at this stage. Revisit only if you have enterprise customers demanding hard isolation.
- **URL routing**: start with path-based tenant routing (`app.yourdomain.com/t/acme-co` for the CRM dashboard, `yourdomain.com/l/acme-co` or a Vercel-generated subdomain for the public landing page). Custom domains per tenant (`acmeco.com` pointing at their landing page) is a Phase 3 feature — Vercel supports this via its Domains API but it adds real complexity (DNS verification, SSL) so it shouldn't block the MVP.

## 4. Data model (MongoDB collections)

**tenants** — company record: name, industry, preferences (from onboarding), chosen template ID, theme config (colors/fonts), subdomain slug, plan/billing status, createdAt.

**users** — login accounts: email, hashed password (or OAuth id), tenantId, role (owner/admin/member).

**leads** — captured from the landing page form: tenantId, name, email, phone, source, custom fields (varies by template/industry), pipeline stage, createdAt.

**contacts** — CRM contacts, similar shape to leads but for people already in the funnel/customers: tenantId, name, company, email, phone, tags, notes, ownerId (which user manages them).

**pipelines** — per-tenant deal/lead stages (e.g. New → Contacted → Qualified → Won/Lost), generated by the agent based on industry, editable after.

**templates** — the library of available landing-page + CRM presets: id, name, industry tags, section layout config, default CSS theme variables, default pipeline stages, preview image.

**agentSessions** — log of the AI agent's onboarding conversation and the config it produced, useful for debugging and for letting a tenant "regenerate" or tweak later.

## 5. Authentication & authorization

**Library**: Auth.js (NextAuth v5). It works natively with the Next.js App Router and ships a MongoDB adapter (`@auth/mongodb-adapter`), so accounts/sessions fit straight into the existing database rather than needing a separate auth service.

**Providers**: Credentials (email + password) as the primary path, since most B2B CRM signups happen directly rather than via social login. Google OAuth as an optional second provider to speed up signup for users who prefer it. Passwords are hashed with bcrypt before being stored on the `users` collection, and the hash field is excluded from normal reads (`select: false` in the schema) so it never accidentally leaks into an API response.

**Session strategy**: JWT, not database-backed sessions. Vercel functions are stateless/serverless, so a JWT avoids a database round-trip on every request. The JWT callback embeds `userId`, `tenantId`, and `role` directly in the token — every request already knows which company it belongs to without an extra query.

**Signup paths**:
- New company → a new tenant is created, the signing-up user becomes `role: owner`.
- Joining an existing company → the user arrives via an invite link (a token encoding tenantId + intended role); completing signup with that token adds them to the existing tenant instead of creating a new one.

**Roles / RBAC**: three roles — `owner`, `admin`, `member`. A small helper (`requireRole(session, ['owner','admin'])`) gates sensitive actions like editing pipeline stages, changing the template/theme, or inviting new users. Members can work leads/contacts but not change tenant-level config.

**Route protection**: `middleware.ts` checks for a valid session on every `/(dashboard)/t/[tenantSlug]` route and redirects to `/login` if missing. Just as important: it verifies the `tenantSlug` in the URL matches the `tenantId` encoded in the session — this is what stops a logged-in user from one company loading another company's dashboard just by editing the URL. Middleware is a first line of defense only; every API route and server action re-checks the session server-side as well, since middleware alone is not a safe authorization boundary.

**Verification & recovery**: email verification on signup and a password-reset flow, both needing a transactional email provider — Resend is a good fit (clean Vercel integration, generous free tier). Verification/reset tokens are stored with an expiry, either in their own collection or via Auth.js's built-in verification-token support in the Mongo adapter.

**Hardening for later** (not needed for MVP, worth planning for): rate-limiting the login/signup endpoints (Upstash Redis + `@upstash/ratelimit` pairs well with Vercel's edge/serverless model), and optionally an account lockout after repeated failed logins. Secure cookie flags (`httpOnly`, `secure`, `sameSite=lax`) are set by Auth.js by default, so no extra work needed there.

**Environment variables needed**: `AUTH_SECRET`, `MONGODB_URI`, `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` (only if Google OAuth is enabled), `RESEND_API_KEY` (only if using Resend for verification/reset emails).

## 6. The AI agent's job

At signup, a short onboarding flow (chat-style or form) collects: industry, company size, what "lead" means for them, tone/style preference, brand colors if any. The agent then:

1. Picks the closest-matching template from the `templates` collection (or ranks a few and lets the user choose).
2. Generates landing page copy (headline, subhead, feature blurbs, CTA text) that fits the template's section structure, via a Claude API call with the template's schema as the expected output shape.
3. Generates a starter pipeline (stage names) and CRM field set appropriate to the industry (e.g. a real-estate CRM wants "property address"; an agency CRM wants "budget").
4. Writes all of this into the tenant's record and creates the pipeline document.

Keeping the agent constrained to filling in a defined schema (rather than free-form code generation) is what keeps this reliable and fast — it's a content/config generator, not a page-layout generator.

## 7. Template/theme system

Each template is a set of React section components (Hero, Features, Testimonials, LeadForm, Footer, etc.) that all read from a single config object — no per-tenant forked code. A tenant's landing page is just: `template component tree` + `tenant's generated config` + `tenant's CSS variables` (colors/fonts injected as a `<style>` block or CSS custom properties). Adding a new template later means adding one more config-driven component set, not touching tenant data.

## 8. Landing page rendering & lead capture

Public landing pages are server-rendered (or statically generated with revalidation) at `/l/[tenantSlug]`, pulling that tenant's config from MongoDB. The lead capture form posts to an API route (`/api/leads`) that validates, tags the tenantId, and inserts into `leads`. From there it shows up in that tenant's CRM immediately.

## 9. CRM application

Standard CRM screens once inside a tenant's dashboard: leads inbox, a kanban-style pipeline board (drag between the agent-generated stages), a contacts table, and basic per-lead detail view with notes/activity. Keep the first version narrow — inbox + pipeline + contact detail — rather than building reporting/analytics up front.

## 10. Repo structure (single Next.js app)

```
/app
  /(marketing)          → your own product's marketing site (not tenant landing pages)
  /(dashboard)/t/[tenantSlug]   → CRM app, auth-gated
  /l/[tenantSlug]        → public tenant landing pages
  /api
    /leads
    /agent               → onboarding + generation endpoints
    /auth
/components
  /templates/[templateId] → section components per template
  /crm                    → dashboard UI components
/lib
  /db.js                  → mongoose connection
  /models                 → Tenant, User, Lead, Contact, Pipeline, Template
  /agent.js                → Claude API calls + prompt schemas
/styles                   → CSS modules, theme variable defaults
```

## 11. Deployment

- GitHub repo, Vercel project linked to it, auto-deploy `main`, PR previews on.
- MongoDB Atlas free tier to start; connection string in Vercel environment variables (`MONGODB_URI`), never committed.
- `ANTHROPIC_API_KEY` also as a Vercel env var for the agent calls.
- Auth secret / NextAuth env vars set the same way.

## 12. Suggested build phases

**Phase 1 (MVP)**: auth + one hardcoded template + manual (non-AI) tenant setup form + basic CRM (leads inbox, simple pipeline, contact list). Goal: prove the full loop — signup → landing page live → lead captured → shows in CRM — works end to end, deployed on Vercel.

**Phase 2**: wire in the actual AI agent — onboarding conversation, Claude-generated copy and pipeline, 2-3 templates to choose from.

**Phase 3**: custom domains per tenant, billing (Stripe), more templates, pipeline customization UI, basic analytics/reporting.

## 13. Open decisions for later

- Billing model (per-tenant subscription tiers, usage limits).
- Whether template selection is agent-only or agent-suggests-and-user-picks.
- Custom domain support timing.
- Team/role permissions beyond owner vs member.
